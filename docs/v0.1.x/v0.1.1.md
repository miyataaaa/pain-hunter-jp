## v0.1.1 変更サマリー

v0.1.0の初回実行レポートから以下の問題が判明し、修正する。

| # | 問題 | 原因 | 修正箇所 |
|---|------|------|----------|
| 1 | クラスタが全てサイズ1（クラスタリングが機能していない） | Extractorの出力が自由記述で長く、完全一致マッチが成立しない | Extractor（プロンプト制約）+ Normalizer + Clusterer |
| 2 | opportunity_scoreの最大値が0.503、しきい値3.8に到達不可能 | サブスコアが0〜1スケールなのにしきい値が1〜5前提 | Scorer + config（OPPORTUNITY_THRESHOLD） |
| 3 | solution_gap_scoreが全クラスタ0.50で横並び | workaroundのキーワード辞書が狭く、デフォルト値に倒れている | Scorer（辞書拡充 or LLMスコア化） |
| 4 | recurrence_scoreが全クラスタ0.11で固定 | クラスタサイズ1 + 出現日数1の直接帰結（問題1が解決すれば連動改善） | Clusterer改善で連動解決 |
| 5 | ジャンル外投稿の混入（ゲーム設定、MOD翻訳等） | カテゴリ内だが対象ニーズではない投稿がすり抜け | **対応しない（v0.1.1方針変更）** |
| 6 | クラスタラベルが長すぎて一覧性がない | job + root_causeの機械的連結 | Report |
| 7 | 接続不能IP確認を全カテゴリで毎回繰り返す（~2分のタイムアウト連打） | 失敗をキャッシュしていないため13カテゴリ×8秒の再探索が発生 | scraper/base.py（IPキャッシュ + フォールバックIP拡充） |

### v0.1.1の方針変更: 「ビジネス文脈限定」を撤廃

v0.1.0では「業務ペイン」のみをis_pain=trueとしていたが、v0.1.1では方針を変更する。

**趣味・ゲーム・個人的な困りごとも含め、「ニーズがあるところ全て」を対象とする。**

理由: このツールの目的は「事業仮説探索」であり、ニーズがある場所にサービスを当て込むことが本質。ゲーム関連でもMOD翻訳でも、繰り返し現れるニーズがあればそれは事業機会になりうる。

したがって、is_painの判定基準は以下に変更する:
- **is_pain: true** = 投稿者が具体的な困りごと・非効率・摩擦を抱えている（ジャンル不問）
- **is_pain: false** = 単なる知識質問（調べれば分かる）、比較・選択相談、感想・雑談

## このツールは何か

Yahoo!知恵袋の投稿から「繰り返し現れる構造的なニーズ」を自動抽出し、
自分が作れるプロダクトアイデアへ変換する個人用CLIツール。

単なる「困りごと収集ツール」ではなく、**事業仮説を探索するエンジン**として設計されている。
1投稿ではなく「複数日にまたがって繰り返し出現するニーズのクラスタ」を評価対象にする点が核心。

## パイプライン全体像

毎朝3時にcronで起動し、以下の8ステップを順番に実行する。
各ステップは独立したJSONを `data/` に出力するため、途中から再実行できる。

```
Yahoo!知恵袋
     │
     ▼
[Step1] Scraper        → data/raw/{date}.json
     │
     ▼
[Step2] Filter         → data/filtered/{date}.json
     │
     ▼
[Step3] Extractor      → data/extracted/{date}.json   ← Claude API  ★v0.1.1で大幅改修
     │
     ▼
[Step4] Normalizer     → data/normalized/{date}.json   ★v0.1.1で辞書更新
     │
     ▼
[Step5] Clusterer      → data/clustered/{date}.json   ← 過去7日分も読む  ★v0.1.1でマッチ緩和
     │
     ▼
[Step6] Scorer         → data/scored/{date}.json       ★v0.1.1でスケール修正
     │
     ▼
[Step7] IdeaGenerator  → data/ideas/{date}.json       ← Claude API（上位3クラスタのみ）
     │
     ▼
[Step8] Report+Notify  → reports/{date}.md + ntfy.sh   ★v0.1.1でラベル短縮
```

## 各ステップの詳細

### Step1: Scraper（`src/scraper/chiebukuro.py`）— v0.1.0から変更なし

**何をするか**: Yahoo!知恵袋の指定カテゴリから質問を収集する。

**対象カテゴリ**: 3ジャンル・13サブカテゴリ
- **コンサル・士業**: 企業と経営 / 会計・経理・財務 / 起業 / 企業法務・知的財産 / 仕事効率化・ノウハウ（職業とキャリア親カテゴリで代替）/ 労働問題、働き方
- **フリーランス・個人事業主**: 税金・年金 / 保険 / インターネットビジネス・SOHO / 法律・消費者問題
- **中小企業のDX**: プログラミング / パソコン / インターネットサービス（旧「サービス、探しています」相当）

**URL構成**（2026年4月時点）:

**HTTPクライアントについて（重要）**:

Python の `requests` ライブラリは TLS フィンガープリントまたは DNS ロードバランシングの問題でタイムアウトする。
具体的には、DNS が返す `183.79.48.x` セグメントの IP が WSL2 環境からブロックされており、
`202.239.2.x` セグメントのみアクセス可能。

`base.py` では raw socket + ssl を使い、以下の順で接続先IPを決定する:

1. DNS解決したIP群を順にTCP接続テスト（4秒タイムアウト）
2. 失敗した場合、`_FALLBACK_IPS` に定義したIP（`202.239.2.249` / `202.239.3.249`）を試みる
3. 成功したIPをセッション内でキャッシュして再利用

この仕組みは `src/scraper/base.py` の `_resolve_working_ip()` に実装されている。

**質問ID抽出**:
カテゴリ一覧ページはJSレンダリングのためBeautifulSoupではリンクが取れない。
ページソースに埋め込まれた `q\d{11,}` パターンのIDをregexで直接抽出する。

**HTMLパース（質問詳細ページ）**:

| 取得情報 | セレクタパターン |
|---|---|
| タイトル | `<h1>` |
| 質問本文 | `div[class~=QuestionItem.*Text]` |
| 回答数 | `[class~=QuestionItem.*Answer]` → `(\d+)回答` |
| 投稿日時 | `[class~=UserInfo.*Date]` |
| 閲覧数 | `[class~=QuestionItem.*Sub]` → `(\d+)閲覧` |

**出力データ（`RawQuestion`）**:
```
source, category_major, category_minor, title, body,
url, answers_count, views, posted_at, scraped_at
```

**制約**:
- robots.txt確認済み、許可パスのみアクセス
- リクエスト間隔2秒以上
- 1回の実行で最大100リクエスト以内
- 本文は500文字で切り捨て（LLM送信時）

### Step2: Filter（`src/filter.py`）— v0.1.0から変更なし

**何をするか**: ノイズ・重複・ペインにならない投稿を除去する。

**除外ルール（この順で適用）**:

| ルール | 条件 |
|---|---|

| スパム | URL3件以上、または宣伝文言マッチ |

### Step3: Extractor（`src/extractor.py`）— ★v0.1.1で大幅改修

**何をするか**: Claude API（`claude-sonnet-4-20250514`）でニーズ情報を構造化する。

#### v0.1.1での変更点

**変更1: is_painの判定基準を拡大**

v0.1.0では「業務ペイン」のみ対象だったが、v0.1.1ではジャンルを問わず「具体的なニーズ」があればis_pain=trueとする。

```
is_pain: true にする条件:
- 投稿者が具体的な困りごと・非効率・摩擦を抱えている
- 趣味、ゲーム、個人の生活上の困りごとも含む
- 「何かを達成しようとしているが、障壁がある」状態

is_pain: false にする条件:
- 単なる知識質問（「〜とは何ですか」型）
- 比較・選択相談（「AとBどちらがいい」型）
- 感想・雑談・議論（具体的な困りごとがない）
- 愚痴のみで具体的な障壁の記述がない
```

**変更2: job_to_be_doneを10文字以内に制約**

v0.1.0ではLLMが「オンライン販売での評価獲得・信頼構築」のような長文を返し、クラスタリングの完全一致マッチが成立しなかった。

v0.1.1ではプロンプトで以下を指示する:
- **10文字以内の短い業務・作業名**で書く
- 動詞で終わる
- 良い例をアンカーとして20個以上提示

```
良い例: 確定申告、請求書作成、契約書レビュー、経費精算、給与計算、
        融資申請、商標出願、見積作成、月次決算、勤怠管理、
        売上集計、在庫管理、顧客対応、採用面接、議事録作成、
        MOD翻訳、PC環境構築、ファイル共有、評価管理、ツール選定
悪い例: オンライン販売での評価獲得・信頼構築（長すぎる）
悪い例: 大容量ファイルの配布・受け渡し（長すぎる）
```

**変更3: root_causeを30文字以内に制約**

同じくLLMの自由記述が長すぎてマッチしないため、制約を追加する。

```
良い例: 制度が複雑でツールが未対応
良い例: 手順が属人化し引き継ぎ不足
良い例: 複数システム間の連携がない
良い例: 法改正に既存ツールが未追従
悪い例: プラットフォーム側のシステム不備で出品者側では制御できない（長すぎる・曖昧）
```

**変更4: current_workaroundを30文字以内に制約**

Scorerのsolution_gap_scoreでキーワードマッチに使うため、出力を短く統一する。

```
良い例: Excelで手動管理、税理士に毎回確認、都度ネット検索、手書きで転記
回避策がない場合: 「対処なし（放置）」
```

**変更5: パース時のバリデーション強化**

- persona_type, pain_category, recurrence_hintのenum値をバリデーション（範囲外はフォールバック）
- job_to_be_doneが15文字超なら10文字に切り詰め（ログ出力あり）
- root_causeが40文字超なら30文字に切り詰め
- current_workaroundが40文字超なら30文字に切り詰め
- severity等の数値スコアを1〜5にクランプ

#### LLMシステムプロンプト（v0.1.1全文）

```
あなたはニーズ分析の専門家です。
日本語のQ&A投稿を読み、そこに「具体的なニーズ（困りごと・非効率・摩擦）」があるかを判定し、
あれば詳細を構造化JSONで返してください。

【判定基準 — is_pain の true/false】

以下はすべて is_pain: false にすること:
- 単なる知識質問（調べれば分かること、「〜とは何ですか」型）
- 比較・選択の相談（「AとBどちらがいい」型）
- 感想・雑談・議論（具体的な困りごとがない）
- 愚痴のみで具体的な障壁の記述がない

以下は is_pain: true にすること（ジャンル不問）:
- 具体的な困りごと・非効率・摩擦を抱えている
- 「何かを達成しようとしているが、障壁がある」状態
- 業務・事務作業、趣味、生活、IT環境など領域は問わない
- 重要: workaround（今どう凌いでいるか）と root_cause（なぜ繰り返すか）を特に重視して抽出すること

【フィールド制約 — 必ず守ること】

■ persona_type: 以下の5択から1つ選ぶ（それ以外は禁止）
  freelancer / consultant / small_biz_owner / employee / other

■ job_to_be_done: **10文字以内**の短い作業名で書く。動詞で終わる。
  良い例: 確定申告、請求書作成、契約書レビュー、経費精算、給与計算、
          融資申請、商標出願、見積作成、月次決算、勤怠管理、
          売上集計、在庫管理、顧客対応、採用面接、議事録作成、
          MOD翻訳、PC環境構築、ファイル共有、評価管理、ツール選定
  悪い例: オンライン販売での評価獲得・信頼構築（長すぎる）

■ pain_category: 以下の11択から1つ選ぶ（それ以外は禁止）
  manual_reentry / document_creation / knowledge_lookup /
  tool_fragmentation / compliance_confusion / approval_bottleneck /
  recurring_admin_work / exception_handling / customer_followup /
  handoff_loss / other

■ root_cause: **30文字以内**で、なぜ繰り返すかの構造的原因を書く。
  良い例: 制度が複雑でツールが未対応
  良い例: 手順が属人化し引き継ぎ不足
  良い例: 複数システム間の連携がない
  悪い例: プラットフォーム側のシステム不備で出品者側では制御できない（長すぎる）

■ current_workaround: **30文字以内**で今の回避策を書く。
  良い例: Excelで手動管理、税理士に毎回確認、都度ネット検索
  回避策がない場合: 「対処なし（放置）」と書く

■ recurrence_hint: 以下の5択から1つ選ぶ
  daily / weekly / monthly / one_off / unknown

■ severity / urgency / willingness_to_pay_proxy / builder_fit: 1〜5の整数
  - severity: 1=軽微, 3=作業が止まることがある, 5=深刻・頻繁に損失が発生
  - urgency: 1=後回しでいい, 3=今週中に解決したい, 5=今すぐ解決したい
  - willingness_to_pay_proxy: 1=無料以外使わない, 3=月額1,000〜5,000円なら, 5=月額1万円以上
  - builder_fit: 1=専門知識が必要, 3=汎用スキルで可能, 5=Python/LLM/APIで十分

出力は必ずJSON配列で返す。各要素のスキーマ:

[
  {
    "question_id": "<question_id>",
    "is_pain": true or false,
    "pain_summary": "ニーズの要約（1〜2文）",
    "persona_type": "上記5択",
    "persona_detail": "例: 建設業の二代目経営者",
    "job_to_be_done": "10文字以内の作業名",
    "pain_stage": "例: 月末処理時、申請準備中",
    "pain_category": "上記11択",
    "current_workaround": "30文字以内",
    "root_cause": "30文字以内",
    "severity": 1〜5,
    "urgency": 1〜5,
    "recurrence_hint": "上記5択",
    "willingness_to_pay_proxy": 1〜5,
    "builder_fit": 1〜5,
    "evidence_text": "根拠となる本文の抜粋（50〜150文字）"
  }
]

is_pain=false の場合、pain_summary以外は空文字列・0でよい。
```

#### パース時のバリデーションロジック（v0.1.1追加）

```python
# enum値のバリデーション
valid_persona = {"freelancer", "consultant", "small_biz_owner", "employee", "other"}
valid_category = {
    "manual_reentry", "document_creation", "knowledge_lookup",
    "tool_fragmentation", "compliance_confusion", "approval_bottleneck",
    "recurring_admin_work", "exception_handling", "customer_followup",
    "handoff_loss", "other",
}
valid_recurrence = {"daily", "weekly", "monthly", "one_off", "unknown"}

# 範囲外はフォールバック
if persona not in valid_persona: persona = "other"
if category not in valid_category: category = "other"
if recurrence not in valid_recurrence: recurrence = "unknown"

# 文字数超過は切り詰め＋ログ
if len(job_to_be_done) > 15: job_to_be_done = job_to_be_done[:10]
if len(root_cause) > 40: root_cause = root_cause[:30]
if len(current_workaround) > 40: current_workaround = current_workaround[:30]

# 数値スコアをクランプ
severity = max(1, min(5, severity))
```

**エラー処理**: v0.1.0から変更なし。APIエラー時はexponential backoffで最大3回リトライ。
JSONパース失敗時は該当バッチを `is_pain=false` のフォールバックで補完。

### Step4: Normalizer（`src/normalizer.py`）— ★v0.1.1で辞書更新

**何をするか**: ニーズの表現ゆれを統一し、クラスタリングできる形に正規化する。

**処理**: ルールベースの同義語辞書で以下のフィールドを正規化する。
- `persona_type` → `canonical_user`
- `job_to_be_done` → `canonical_job`
- `pain_category` → `canonical_problem`
- `root_cause` → `canonical_root_cause`

root_causeも正規化対象に加える。Extractorが30文字以内で出すため、部分一致ベースで辞書を適用できる。

ROOT_CAUSE_PATTERNS = {

```

**出力データ（`NormalizedPain`）**: v0.1.0から変更なし。
```
pain_id, question_id, canonical_problem, canonical_user,

### Step5: Clusterer（`src/clusterer.py`）— ★v0.1.1でマッチ緩和

**何をするか**: 類似ニーズを束ねて「繰り返すテーマ」としてのクラスタを作る。

#### v0.1.1での変更点

**変更1: Phase 1のマッチキーを `canonical_job` 単独に変更**

v0.1.0では `canonical_job + canonical_root_cause` の完全一致だった。
しかし同じ「確定申告」の困りごとでも root_cause が微妙に異なるとクラスタが分裂していた。

v0.1.1では `canonical_job` のみで第一段階のグルーピングを行う。
root_cause はクラスタ内の要約情報として保持するが、マッチキーには使わない。

```
v0.1.0: groupby(canonical_job + canonical_root_cause) → 全てサイズ1
v0.1.1: groupby(canonical_job) → 同じ作業の困りごとがまとまる
```

**変更2: Phase 2（タグ近傍合流）のしきい値調整**

Phase 1でシングルトンになったクラスタを、タグ一致数が **1以上** の既存マルチクラスタへ合流させる（v0.1.0は2以上）。

**変更3: Phase 3（pain_category合流）を新設**

Phase 2後もシングルトンのものについて、`canonical_problem`（= pain_category）が同一のクラスタ同士を合流させる。
これにより「同じ種類の課題」が緩やかにまとまる。

```
Phase 1: canonical_job 完全一致 → グルーピング
Phase 2: シングルトンをタグ近傍（1以上一致）でマルチクラスタへ合流
Phase 3: 残りシングルトンを canonical_problem 一致でグルーピング
```

**過去7日分との合流**: v0.1.0から変更なし。
当日データだけでなく、`data/normalized/` から過去7日分を読み込んで合流させる。

**出力データ（`PainCluster`）**: v0.1.0から変更なし。
```
cluster_id, cluster_label, canonical_problem,
representative_user, representative_job, root_cause_summary,
question_ids, pain_ids, cluster_size
（スコアフィールドはStep6で計算、この時点は仮値0.0）
```

#### cluster_label の生成ルール（v0.1.1追加）

v0.1.0ではjob + root_causeの機械的連結で長すぎるラベルが生成されていた。
v0.1.1では以下のルールでラベルを生成する:

```

例: 「確定申告」「ファイル共有」「PC環境構築」
```

root_causeやpain_categoryはラベルには含めず、クラスタの詳細表示時に別途表示する。

### Step6: Scorer（`src/scorer.py`）— ★v0.1.1でスケール修正

**何をするか**: 各クラスタの「事業機会としての価値」をスコア化する。

**合成式**: v0.1.0から変更なし。
```python
opportunity_score = (
    0.20 * severity_score
    + 0.20 * recurrence_score
    + 0.20 * solution_gap_score
    + 0.15 * wtp_score
    + 0.15 * builder_fit_score
    + 0.10 * productability_score
)
```

#### v0.1.1での変更点

**変更1: OPPORTUNITY_THRESHOLDのスケール修正**

各サブスコアの出力レンジは0〜1のため、opportunity_scoreの理論最大値は1.0。
v0.1.0の3.8は1〜5スケールの値を誤って設定していた。

```
v0.1.0: OPPORTUNITY_THRESHOLD=3.8（到達不可能）
v0.1.1: OPPORTUNITY_THRESHOLD=0.65
```

**変更2: solution_gap_scoreのキーワード辞書拡充**

v0.1.0ではExcel・手動・手書き等の狭いキーワードしかなく、全クラスタ0.50のデフォルト値に倒れていた。
v0.1.1では以下のパターンを追加する。

```python
# 高スコア（代替手段が弱い = 事業機会がある）→ 0.7〜1.0
HIGH_GAP_KEYWORDS = [
    "手動", "手作業", "手書き", "Excel", "エクセル",
    "毎回", "都度", "ゼロから",
    "対処なし", "放置", "我慢", "泣き寝入り",
    "自力で調べ", "ネット検索", "毎回聞", "都度確認",
    "紙", "FAX", "電話で確認",
]

# 低スコア（既存の解決策がある = 参入が難しい）→ 0.1〜0.3
LOW_GAP_KEYWORDS = [
    "SaaS", "専用ソフト", "専用ツール", "専用アプリ",
    "freee", "マネーフォワード", "弥生",
    "自動化済み", "API連携",
]

# どちらにもマッチしない場合 → 0.50（v0.1.0と同じデフォルト）
```

**変更3: wtp_score / builder_fit_scoreのスケール方法を明文化**

v0.1.0ドキュメントに記載がなかったため追加:

```python
wtp_score = (avg_willingness_to_pay_proxy - 1) / 4.0  # 0〜1にスケール
builder_fit_score = (avg_builder_fit - 1) / 4.0        # 0〜1にスケール
```

**各スコアの計算方法（v0.1.1完全版）**:

| スコア | 計算方法 | レンジ |
|---|---|---|
| `severity_score` | `(avg_severity - 1) / 4.0` | 0〜1 |
| `recurrence_score` | `min(1.0, cluster_size / 10) × 0.7 + min(1.0, 出現日数 / LOOKBACK_DAYS) × 0.3` | 0〜1 |
| `solution_gap_score` | workaroundキーワードマッチ（上記辞書）| 0〜1 |
| `wtp_score` | `(avg_willingness_to_pay_proxy - 1) / 4.0` | 0〜1 |
| `builder_fit_score` | `(avg_builder_fit - 1) / 4.0` | 0〜1 |
| `productability_score` | recurrence_hint分布から（daily=1.0, weekly=0.8, monthly=0.6, one_off=0.2, unknown=0.4） | 0〜1 |

v0.1.0から変更なし。

import socket
socket.getaddrinfo('chiebukuro.yahoo.co.jp', 443, socket.AF_INET)

## 設計上の重要な判断

**「単発投稿」ではなく「クラスタ」を評価単位にした理由**:
1日1件の投稿から見える課題は偶発的な可能性がある。
同じ課題が複数日・複数人から出続けているものだけが「構造的に解決されていない課題」であり、
事業仮説として信頼性が高い。

**`current_workaround` と `root_cause` を重視した理由**:
「困っている」だけなら解決策がすでにあるかもしれない。
「Excelで手動管理している」「専門家に毎回聞いている」という回避策の弱さが、
そのまま市場の空白になる。

**Extractorで「知識不足」を明示的に除外した理由**:
「〜とは何ですか」型の質問は情報提供で解決できるが、
業務フローや制度の構造問題は情報提供では解決しない。
後者だけが継続的な課題（=プロダクトのターゲット）になる。

**raw socket + ssl を選んだ理由**:
`requests` / `http.client` はOS標準のDNS解決経由で接続し、
ブロックされているIPセグメントに当たると全リクエストがタイムアウトする。
raw socketでIPを直接指定することでDNSロードバランシングの影響を回避できる。

### v0.1.1で追加した判断

**ニーズ対象をビジネス領域に限定しない理由**:
このツールの目的は「事業仮説探索」であり、ニーズがある場所にサービスを当て込むことが本質。
趣味・ゲーム・個人の生活上の困りごとも、繰り返し出現するなら事業機会になりうる。
フィルタリングは「ニーズの有無」で行い、「ジャンルの適否」では行わない。

**クラスタリングのマッチキーをcanonical_job単独にした理由**:
v0.1.0では `canonical_job + canonical_root_cause` の完全一致だったが、
同じ作業の困りごとでもroot_causeが微妙に異なると別クラスタに分裂していた。
「同じ作業で困っている人が複数いる」こと自体が事業機会のシグナルであり、
root_causeはクラスタ内で集約して分析すればよい。

**Extractorの出力を短文に制約した理由**:
LLMの自由記述はクラスタリングの敵。完全一致マッチを成立させるには、
出力のバリエーションを減らす必要がある。10文字制約 + 良い例のアンカリングで
LLMの出力を収束させ、クラスタが自然に育つ設計にした。
LLMの出力分散を大幅に抑制できる。パース時の切り詰めは保険。
