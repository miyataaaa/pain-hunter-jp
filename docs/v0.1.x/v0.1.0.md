# PainHunter JP v1 — 仕組みドキュメント

> **最終更新**: 2026-04-05（初回実行完了・スクレイパー刷新後）

## このツールは何か

Yahoo!知恵袋の投稿から「繰り返し現れる構造的な業務課題」を自動抽出し、
自分が作れるプロダクトアイデアへ変換する個人用CLIツール。

単なる「困りごと収集ツール」ではなく、**事業仮説を探索するエンジン**として設計されている。
1投稿ではなく「複数日にまたがって繰り返し出現するペインのクラスタ」を評価対象にする点が核心。

---

## パイプライン全体像

毎朝3時にcronで起動し、以下の8ステップを順番に実行する。
各ステップは独立したJSONを `data/` に出力するため、途中から再実行できる。

```
Yahoo!知恵袋
     │
     ▼
[Step1] Scraper        → data/raw/{date}.json
     │
     ▼
[Step2] Filter         → data/filtered/{date}.json
     │
     ▼
[Step3] Extractor      → data/extracted/{date}.json   ← Claude API
     │
     ▼
[Step4] Normalizer     → data/normalized/{date}.json
     │
     ▼
[Step5] Clusterer      → data/clustered/{date}.json   ← 過去7日分も読む
     │
     ▼
[Step6] Scorer         → data/scored/{date}.json
     │
     ▼
[Step7] IdeaGenerator  → data/ideas/{date}.json       ← Claude API（上位3クラスタのみ）
     │
     ▼
[Step8] Report+Notify  → reports/{date}.md + ntfy.sh
```

## 各ステップの詳細

### Step1: Scraper（`src/scraper/chiebukuro.py`）

**何をするか**: Yahoo!知恵袋の指定カテゴリから質問を収集する。

**対象カテゴリ**: 3ジャンル・13サブカテゴリ
- **コンサル・士業**: 企業と経営 / 会計・経理・財務 / 起業 / 企業法務・知的財産 / 仕事効率化・ノウハウ（職業とキャリア親カテゴリで代替）/ 労働問題、働き方
- **フリーランス・個人事業主**: 税金・年金 / 保険 / インターネットビジネス・SOHO / 法律・消費者問題
- **中小企業のDX**: プログラミング / パソコン / インターネットサービス（旧「サービス、探しています」相当）

**URL構成**（2026年4月時点）:

| 用途 | URL |
|---|---|
| カテゴリ一覧 | `https://chiebukuro.yahoo.co.jp/category/{cid}/question/list` |
| 質問詳細 | `https://detail.chiebukuro.yahoo.co.jp/qa/question_detail/{qid}` |

> **注意**: 旧URL `/ct/cid/{old_id}/new/` は廃止（404）。カテゴリIDも全面刷新されている。
> 質問詳細はサブドメイン `detail.chiebukuro.yahoo.co.jp` に移行済み。

**カテゴリID一覧（新体系）**:

| 大カテゴリ | 中カテゴリ | CID |
|---|---|---|
| ビジネス、経済とお金 | 企業と経営 | 2078297793 |
| ビジネス、経済とお金 | 会計、経理、財務 | 2078297803 |
| ビジネス、経済とお金 | 起業 | 2078297806 |
| ビジネス、経済とお金 | 企業法務、知的財産 | 2078297805 |
| 職業とキャリア | 仕事効率化・ノウハウ | 2078297897 |
| 職業とキャリア | 労働問題、働き方 | 2078297899 |
| ビジネス、経済とお金 | 税金、年金 | 2080401772 |
| ビジネス、経済とお金 | 保険 | 2080401781 |
| ビジネス、経済とお金 | インターネットビジネス、SOHO | 2078297802 |
| 暮らしと生活ガイド | 法律、消費者問題 | 2078297944 |
| コンピュータテクノロジー | プログラミング | 2078297622 |
| スマートデバイス、PC、家電 | パソコン | 2080401529 |
| インターネット、通信 | インターネットサービス | 2080401307 |

**HTTPクライアントについて（重要）**:

Python の `requests` ライブラリは TLS フィンガープリントまたは DNS ロードバランシングの問題でタイムアウトする。
具体的には、DNS が返す `183.79.48.x` セグメントの IP が WSL2 環境からブロックされており、
`202.239.2.x` セグメントのみアクセス可能。

`base.py` では raw socket + ssl を使い、以下の順で接続先IPを決定する:

1. DNS解決したIP群を順にTCP接続テスト（4秒タイムアウト）
2. 失敗した場合、`_FALLBACK_IPS` に定義したIP（`202.239.2.249` / `202.239.3.249`）を試みる
3. 成功したIPをセッション内でキャッシュして再利用

この仕組みは `src/scraper/base.py` の `_resolve_working_ip()` に実装されている。

**質問ID抽出**:
カテゴリ一覧ページはJSレンダリングのためBeautifulSoupではリンクが取れない。
ページソースに埋め込まれた `q\d{11,}` パターンのIDをregexで直接抽出する。

**HTMLパース（質問詳細ページ）**:

| 取得情報 | セレクタパターン |
|---|---|
| タイトル | `<h1>` |
| 質問本文 | `div[class~=QuestionItem.*Text]` |
| 回答数 | `[class~=QuestionItem.*Answer]` → `(\d+)回答` |
| 投稿日時 | `[class~=UserInfo.*Date]` |
| 閲覧数 | `[class~=QuestionItem.*Sub]` → `(\d+)閲覧` |

**出力データ（`RawQuestion`）**:
```
source, category_major, category_minor, title, body,
url, answers_count, views, posted_at, scraped_at
```

**制約**:
- robots.txt確認済み、許可パスのみアクセス
- リクエスト間隔2秒以上
- 1回の実行で最大100リクエスト以内
- 本文は500文字で切り捨て（LLM送信時）

### Step2: Filter（`src/filter.py`）

**何をするか**: ノイズ・重複・ペインにならない投稿を除去する。

**除外ルール（この順で適用）**:

| ルール | 条件 |
|---|---|
| 短すぎる | 本文30文字未満 |
| スパム | URL3件以上、または宣伝文言マッチ |
| 過去URL | 過去7日以内に取得済みのURL |
| 知識質問 | 「〜とは何ですか」「意味を教えて」パターン（タイトルのみ）|
| 比較質問 | 「どちらが良い」「AとBを比較」パターン |
| 低情報量 | 本文がほぼタイトルと同じ（類似度0.85以上かつ80文字未満）|
| 重複 | `difflib.SequenceMatcher`で類似度0.8以上の本文を持つ投稿 |

**なぜ知識質問と比較質問を除くか**:
これらは「今困っている」のではなく「調べている」状態。
繰り返す構造的課題を見つけたいので、具体的な業務上の摩擦を含む投稿だけ残す。

---

### Step3: Extractor（`src/extractor.py`）

**何をするか**: Claude API（`claude-sonnet-4-20250514`）でペイン情報を構造化する。

**処理方式**: 5件ずつバッチにまとめてAPIに送信（コスト削減）。

**LLMへの主な指示**:
- 「単なる知識不足」はペインではない（`is_pain: false`）
- 「構造的に繰り返す課題」のみペイン（`is_pain: true`）
- `current_workaround`（今どう凌いでいるか）と `root_cause`（なぜ繰り返すか）を特に重視して抽出

**出力データ（`ExtractedPain`）の主要フィールド**:

| フィールド | 説明 |
|---|---|
| `is_pain` | ペインかどうかの判定 |
| `pain_summary` | ペインの要約（1〜2文）|
| `persona_type` | freelancer / consultant / small_biz_owner / employee / other |
| `job_to_be_done` | 何の作業をしようとしているか（例: 請求書作成）|
| `current_workaround` | 今どう凌いでいるか（例: Excelで手動管理）|
| `root_cause` | なぜこの問題が繰り返すか |
| `severity` | 深刻度 1〜5 |
| `recurrence_hint` | daily / weekly / monthly / one_off / unknown |
| `willingness_to_pay_proxy` | 支払意欲の代理変数 1〜5 |
| `builder_fit` | Python/LLMで作れる度 1〜5 |

**エラー処理**: APIエラー時はexponential backoffで最大3回リトライ。
JSONパース失敗時は該当バッチを `is_pain=false` のフォールバックで補完。

---

### Step4: Normalizer（`src/normalizer.py`）

**何をするか**: ペインの表現ゆれを統一し、クラスタリングできる形に正規化する。

**処理**: ルールベースの同義語辞書で以下のフィールドを正規化する。
- `persona_type` → `canonical_user`
- `job_to_be_done` → `canonical_job`
- `pain_category` → `canonical_problem`
- `root_cause` → `canonical_root_cause`

**なぜ必要か**: LLMが「確定申告」「確定申告の作業」「毎年の確定申告」と表現ゆれで返してきても、
正規化後に `確定申告` で統一されれば同じクラスタに入る。

**出力データ（`NormalizedPain`）**:
```
pain_id, question_id, canonical_problem, canonical_user,
canonical_job, canonical_root_cause, tags
```

---

### Step5: Clusterer（`src/clusterer.py`）

**何をするか**: 類似ペインを束ねて「繰り返すテーマ」としてのクラスタを作る。

**2フェーズのクラスタリング**:

**Phase 1（完全一致グルーピング）**:
`canonical_job + canonical_root_cause` が完全に一致するペインを同一クラスタに束ねる。

**Phase 2（タグ近傍合流）**:
Phase 1でシングルトン（1件クラスタ）になったものを、
タグ一致数が2以上の既存マルチクラスタへ合流させる試み。

**過去7日分との合流**:
当日データだけでなく、`data/normalized/` から過去7日分を読み込んで合流させる。
これにより「3日連続で同じ課題が出ている」といったトレンドを検出できる。

**出力データ（`PainCluster`）の主要フィールド**:
```
cluster_id, cluster_label, canonical_problem,
representative_user, representative_job, root_cause_summary,
question_ids, pain_ids, cluster_size
（スコアフィールドはStep6で計算、この時点は仮値0.0）
```

---

### Step6: Scorer（`src/scorer.py`）

**何をするか**: 各クラスタの「事業機会としての価値」をスコア化する。

**合成式**:
```python
opportunity_score = (
    0.20 * severity_score       # 深刻度の平均
    + 0.20 * recurrence_score   # 繰り返し性（件数×出現日数）
    + 0.20 * solution_gap_score # 現在の代替手段の弱さ
    + 0.15 * wtp_score          # 支払意欲の平均
    + 0.15 * builder_fit_score  # 自分が作れる度の平均
    + 0.10 * productability_score  # プロダクト化しやすさ
)
```

**各スコアの計算方法**:

| スコア | 計算方法 |
|---|---|
| `severity_score` | `(avg_severity - 1) / 4.0` で0〜1にスケール |
| `recurrence_score` | `cluster_size / 10 × 0.7 + 出現日数 / LOOKBACK_DAYS × 0.3` |
| `solution_gap_score` | `current_workaround` にExcel・手動・手書き等のキーワードがあると高スコア、SaaS・専用ソフトがあると低スコア |
| `productability_score` | `recurrence_hint` の分布から（daily=1.0, weekly=0.8, monthly=0.6, one_off=0.2）|

最終出力は `opportunity_score` 降順でソートされる。

---

### Step7: IdeaGenerator（`src/idea_generator.py`）

**何をするか**: スコア上位3クラスタのみを対象に、具体的なプロダクトアイデアを生成する。

**上位3件だけ処理する理由**: APIコストの最適化。低スコアのクラスタはアイデア化する価値が低い。

**出力データ（`IdeaCandidate`）の主要フィールド**:
```
idea_title, one_liner, target_user, problem_statement,
solution, mvp_scope, revenue_model, estimated_price,
tech_stack, mvp_days, moat, key_risks, why_now
```

---

### Step8: Report + Notify（`src/report.py`, `src/notifier.py`）

**何をするか**: 日次Markdownレポートを生成し、ntfy.shで通知する。

- レポートは `reports/{date}.md` に保存
- ntfy.shにHTTPS POSTでサマリーを送信（通知アプリで朝に受け取れる）

**注意**: ntfy.sh の `Title` ヘッダーには日本語を直接渡せない（HTTP ヘッダーは latin-1）。
`urllib.parse.quote()` でURLエンコードして渡す。

## データフロー図（1件の投稿が辿る経路）

```
Yahoo!知恵袋の投稿（HTML）
  │
  ▼
RawQuestion（タイトル・本文・URL・カテゴリ）
  │ フィルタ通過
  ▼
RawQuestion（filtered）
  │ Claude APIでペイン構造化
  ▼
ExtractedPain（is_pain=true の場合のみ後続へ）
  │ 同義語辞書で表現ゆれ統一
  ▼
NormalizedPain（canonical_job / canonical_root_cause）
  │ 同一キーを持つものを束ねる
  ▼
PainCluster（複数のNormalizedPainの集合）
  │ 6指標で機会スコア算出
  ▼
PainCluster（opportunity_score付き）
  │ 上位3クラスタのみ
  ▼
IdeaCandidate（MVP案・収益モデル・技術スタック）
  │
  ▼
reports/{date}.md + ntfy.sh通知
```

## 既知の問題・運用上の注意

### スクレイパーのネットワーク到達性

Yahoo!知恵袋のDNSは `183.79.48.x` 系のIPを返すことが多いが、
WSL2環境（および一部クラウド環境）からはこのセグメントへのTCP接続がブロックされる場合がある。
`202.239.2.x` 系のIPなら到達可能であることが多い。

`base.py` の `_FALLBACK_IPS` に動作確認済みIPを記録しているが、
Yahoo! JAPANのCDN構成変更により将来的に無効になる可能性がある。
接続エラーが続く場合は以下で到達可能なIPを確認すること:

```python
import socket
socket.getaddrinfo('chiebukuro.yahoo.co.jp', 443, socket.AF_INET)
```

### カテゴリIDの変更

Yahoo!知恵袋はサイトリニューアルでカテゴリURLとIDを変更した（2025年ごろ）。
旧ID（`2001050000` 形式）は全て404。
新ID（`2078297xxx` / `2080401xxx` 形式）を `CATEGORIES` リストに定義済み。

## 設計上の重要な判断

**「単発投稿」ではなく「クラスタ」を評価単位にした理由**:
1日1件の投稿から見える課題は偶発的な可能性がある。
同じ課題が複数日・複数人から出続けているものだけが「構造的に解決されていない課題」であり、
事業仮説として信頼性が高い。

**`current_workaround` と `root_cause` を重視した理由**:
「困っている」だけなら解決策がすでにあるかもしれない。
「Excelで手動管理している」「専門家に毎回聞いている」という回避策の弱さが、
そのまま市場の空白になる。

**Extractorで「知識不足」を明示的に除外した理由**:
「〜とは何ですか」型の質問は情報提供で解決できるが、
業務フローや制度の構造問題は情報提供では解決しない。
後者だけが継続的な課題（=プロダクトのターゲット）になる。

**raw socket + ssl を選んだ理由**:
`requests` / `http.client` はOS標準のDNS解決経由で接続し、
ブロックされているIPセグメントに当たると全リクエストがタイムアウトする。
raw socketでIPを直接指定することでDNSロードバランシングの影響を回避できる。
